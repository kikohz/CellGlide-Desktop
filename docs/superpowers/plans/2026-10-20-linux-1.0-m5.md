# Linux 1.0 · M5 发布 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 Linux 版作为 1.0.0 正式版发布到 pkg.cellglide.com，并让官网能下载。工作分四块：
- 版本号与许可清单收尾；
- 发布脚本生成下载数据 `release-linux.json`；
- 官网加 Linux 下载区、更新日志，首页从「即将推出」改为可下载；
- 六个发行版的安装清单。

**Architecture:** 构建、签名、上传继续用 M2 的 `build-packages.sh` 和 `sign-and-publish.sh`：两种架构分别在两台机器上构建，签名钥匙只在 Mac 上。
- spec 要的 `scripts/release.py` 收窄为 `scripts/release-linux-json.py`，只做一件事：从 `dist/<版本>/` 生成 `release-linux.json`。
- `sign-and-publish.sh` 在真实上传成功后调用它，把结果写到 `dist/<版本>/release-linux.json`。
- 官网（CellProxy `Website/build.py`）在构建时读这份文件（复制到 `Website/release-linux.json`），照 Mac 的 `release.json` 的做法生成下载区。
- 发布动作由用户在自己的终端执行，每一步都是用户确认的关口。

**Tech Stack:** Rust 工作区（只改版本号）；POSIX sh 与 Python 3 标准库（`unittest`）；官网是 Python 静态生成器加 Cloudflare Workers（`npm run deploy`）；用 Lima 虚拟机（arm64）、测试机（Ubuntu 26.04 x86_64）和 podman 构建容器。

**Spec:** `docs/specs/2026-10-16-linux-1.0-full-design.md` 的 §2、§5 M5 行和 §8。它沿用 `docs/specs/2026-10-15-linux-1.0-design.md` 的 §3.10（发布脚本、官网下载页）和 §5（多发行版安装测试）。M4 遗留见 `docs/validation/linux-1.0-m4-execution-notes.md`「留下的小问题」和 `docs/validation/linux-1.0.md`「留到 M5」。

**计划层面的决定（执行者照此做）：**

1. **不写一体的 `release.py`。** 两种架构在两台机器上构建：arm64 在 Mac 的 Docker 里，x86_64 在测试机的 podman 里。签名钥匙只在 Mac，口令由用户输入。一个脚本串起全部步骤，反而会把跨机器的步骤藏起来。新脚本只负责生成下载数据，其余沿用已在 beta 中验证过的两个脚本。
2. **`release-linux.json` 的格式**（官网只依赖这些字段）：

   ```json
   {
     "version": "1.0.0",
     "date": "2026-10-2X",
     "files": [
       {"kind": "deb", "arch": "amd64",   "url": "https://pkg.cellglide.com/apt/pool/main/c/cellglide/cellglide_1.0.0-1_amd64.deb", "size": 0, "sha256": "…"},
       {"kind": "deb", "arch": "arm64",   "url": "https://pkg.cellglide.com/apt/pool/main/c/cellglide/cellglide_1.0.0-1_arm64.deb", "size": 0, "sha256": "…"},
       {"kind": "rpm", "arch": "x86_64",  "url": "https://pkg.cellglide.com/rpm/x86_64/cellglide-1.0.0-1.x86_64.rpm", "size": 0, "sha256": "…"},
       {"kind": "rpm", "arch": "aarch64", "url": "https://pkg.cellglide.com/rpm/aarch64/cellglide-1.0.0-1.aarch64.rpm", "size": 0, "sha256": "…"}
     ]
   }
   ```

   - `version` 用 Cargo 写法（`1.0.0-beta.2` 这种），官网直接显示它。
   - `files` 固定为四项，顺序如上。
   - rpm 的 `size` 和 `sha256` 取 `signed.noindex/<pkgver>/` 里签过名的那份，因为那才是线上的字节；deb 的取 `dist/<pkgver>/`。
   - URL 中的 `~` 原样保留（beta 的 rpm 直链已证明可用）。
3. **官网开发期间用 beta.2 的真实数据。** beta.2 已经在线，链接都能打开。先用 `release-linux.json --version 1.0.0~beta.2` 生成一份放进 Website，用它开发和检查。正式发布那一步（Task 6）再换成 1.0.0。官网在 1.0.0 发布前**不部署**。
4. **官网三种语言都写**（zh、en、es，官网现有三种）。App 本身没有西班牙语（spec §2），不影响官网。英文、西班牙文由执行者写，控制者审。
5. **升级提示。** 从 beta 升到 1.0.0 时，正在运行的旧界面不持有 `com.cellglide.Gui`，第一次从应用列表打开会多出一个托盘图标（M4 执行记录）。更新日志写一句「升级后请注销或重启一次」，README 的升级说明也写。
6. **M4 留下的 minor 8 在本里程碑修**（P36）：偏好写盘、测速记录读写移出界面线程。
7. **R2 里的三份测试诊断报告**（CG-FEX8W、CG-J9U6G、CG-3ZFV4）是否删除，在 Task 6 结尾问用户，不自行删除。

## Global Constraints

- `AGENTS.md`（CellProxy 根目录）全部适用：
  - 只动 `cellglide0` 的 DNS 和 realm 198 的路由；
  - 每次在测试机上安装或测试，前后各跑一次 `scripts/network-snapshot.sh`，两次结果一致；
  - 替换程序前先停服务，并确认 `cellglide0` 已经消失。
- 签名私钥只在 Mac 的 GnuPG 里。`sign-and-publish.sh` 由**用户在自己的终端**运行（需要输入口令）；控制者给出完整命令，不代跑。
- **对外动作每一步都先问用户**，未经确认不执行：
  - 上传到 R2；
  - 部署官网；
  - 推送分支或标签；
  - 合并到 main；
  - 删除 R2 对象。
- 部署官网用 Website 自带的 wrangler：先 `npm ci`，再 `npm run deploy`，不用全局 npx 的旧版本（M3 事故）。
- CellProxy 是共用目录，`AGENTS.md`、`CLAUDE.md`、`.claude/` 不是本工作的改动，不碰也不提交。官网改动在 CellProxy 新分支 `linux-download` 上做：在主目录 `git switch -c`，不另建 worktree。只 `git add` 自己的文件。
- 版本号只有一个来源：`Cargo.toml` `[workspace.package] version`。正式版写 `1.0.0`，包版本由 `scripts/pkg-version.sh` 推出。
- 改了 `Cargo.lock` 之后必须重跑 `scripts/update-licenses.sh`（需要 cargo-about 0.9.2），并提交结果。
- 官网的截图、视频只用英文界面（本里程碑不计划新截图）。
- 官网正文里的支持范围照 README：
  - Debian / Ubuntu 用 deb，Fedora 42 及以上用 rpm；
  - x86_64 与 arm64；
  - 需要 systemd 和 glibc 2.35 或更新。
- 每个代码任务结束前要通过：
  - CellGlide-Desktop：`cargo fmt --all`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`，以及 `scripts/linux-test.sh`；
  - 官网：`python3 build.py && python3 check.py && node --test language.test.cjs`。

## Review Focus

1. **升级版本排序。** apt 和 dnf 都必须把 `1.0.0` 判为比 `1.0.0~beta.2` 新，否则 beta 用户收不到更新。Task 5 用 `dpkg --compare-versions` 和 `rpmdev-vercmp`（或 `rpm --eval '%{lua:print(rpm.vercmp(...))}'`）各验一次，再做一次从 beta.2 到 1.0.0 的真实升级。
2. **文件名推导。** 正式版文件名里没有 `~`，`release-linux.json` 的生成器必须用 `dist/` 里真实存在的文件名，不能靠拼字符串推测。Task 2 的测试同时覆盖 beta 和正式两种文件名，并在缺文件或多文件时报错。
3. **官网缺数据时必须构建失败。** `release-linux.json` 缺失、少一个架构或字段错时，`build.py` 要直接失败，不能生成链接为空的页面。Task 3 给出对应测试。
4. **架构标注要清楚。** Fedora 和 arm64 用户在下载区要能一眼分清四个包：每行都写出发行版类型和架构，例如「Debian / Ubuntu · x86_64 (amd64)」。Task 3 的检查断言四行标签互不相同，且都带 sha256。
5. **Mac 更新源不受影响。** Linux 的更新日志不能进入 Mac 的 Sparkle `appcast.xml`。Task 3 断言 appcast 里只有 `platform == 'mac'` 的条目。

- `--pkgver` 和 `version` 的关系：把 `pkgver` 中第一个 `~` 换成 `-` 即得 `version`。
- Python 函数：`build(root: Path, pkgver: str, date: str, base: str) -> dict`，产出决定 2 规定的结构。出错时抛 `ReleaseDataError(message)`，命令行把它变成退出码 1 加一行错误信息。
- 下游：Task 3 读这份数据，Task 6 用它发布。

- [ ] **Step 1: 写失败测试，全部用临时目录伪造 `dist/` 和 `signed.noindex/`。**
  - `test_final_names`：`pkgver="1.0.0"`、文件 `cellglide_1.0.0-1_amd64.deb` 等四个都在时，`version == "1.0.0"`，四个 URL 依次等于决定 2 中的四条，`size` 和 `sha256` 与文件字节一致。
  - `test_beta_names`：`pkgver="1.0.0~beta.2"` 时，`version == "1.0.0-beta.2"`，rpm 的 URL 是 `…/rpm/x86_64/cellglide-1.0.0~beta.2-1.x86_64.rpm`。
  - `test_rpm_hash_from_signed`：`signed.noindex` 里 rpm 的字节和 `dist` 里不同时，`sha256` 取 signed 那份。
  - `test_missing_arch_fails`：少了 arm64 deb 时抛出 `ReleaseDataError`，信息里含 `arm64`。
  - `test_two_matches_fails`：同一架构有两个 deb 时抛出 `ReleaseDataError`。
  - `test_checksum_mismatch_fails`：`SHA256SUMS.x86_64` 里记的 deb 哈希与文件不符时抛出 `ReleaseDataError`。
- [ ] **Step 2: 运行测试确认失败。** `python3 -m unittest scripts/tests/test_release_linux_json.py` 应因模块不存在而失败。

  - deb 的哈希要和 `SHA256SUMS.<arch>` 交叉校验。
  - 输出 JSON：缩进 2 格，`ensure_ascii=False`，末尾带换行。
- [ ] **Step 4: 运行测试确认通过。** 上面的 unittest 全部通过。
